# Адмінська редакція: локальна структура і seed-only Supabase

## Головне правило

Назва, тип, підпорядкування, штатний скелет та інші параметри підрозділу
зберігаються локально на комп’ютері адміністратора. Для них немає окремих
серверних таблиць або JSON-колонок.

Адмінська програма формує з локальної картки один самодостатній сід формату
SHU1. Сервер бачить і зберігає його як непрозорий рядок. Після активації
клієнтська програма отримує цей рядок і локально відновлює з нього скелет.

## Точний потік

1. Адміністратор локально створює назву, тип і скелет підрозділу.
2. Адмінська програма серіалізує все це в один deployment seed.
3. На сервер надсилається тільки seed та ознака випуску основного коду.
4. Сервер зберігає сід як opaque text, обчислює digest і генерує короткий
   одноразовий код активації.
5. Адміністратор передає користувачу короткий код, а не довгий сід.
6. Під час першого запуску користувач вводить код.
7. Клієнт надсилає code, installationUid та appVersion.
8. Сервер перевіряє код, позначає його використаним і повертає seed,
   seedVersion та deviceToken.
9. Клієнт декодує сід локально й створює назву, тип і скелет у власній БД.
10. Наступні запити виконуються через технічний device token інсталяції.

Сервер не будує і не аналізує структуру. Відновлення реалізоване у файлі
src/features/admin/deploymentSeed.ts функцією decodeDeploymentSeed.

## Що зберігається де

| Дані | Комп’ютер адміністратора | Supabase | Комп’ютер користувача |
| --- | --- | --- | --- |
| Назва, тип, скелет | Так | Ні, лише всередині opaque seed | Так, після декодування |
| Повна локальна картка | Так | Ні | Ні |
| Deployment seed | Формується локально | Так, одним рядком | Отримується при активації |
| Короткий код | Показується один раз | Лише HMAC і підказка | Вводиться один раз |
| Статуси кодів | Кешуються | Так | Локальний статус |
| Агреговані цифри | За потреби | Так | Відправляються вручну |

Через локальне зберігання карток обов’язково потрібен експорт/резервна копія
адмінської бази.

## Таблиці Supabase

Міграція: supabase/migrations/202609240001_admin_control_plane.sql.

| Таблиця | Призначення |
| --- | --- |
| unit_deployments | Поточний opaque seed, digest, версія та статус. Без колонок назви чи структури. |
| unit_seed_revisions | Попередні версії opaque seed. |
| unit_activation_codes | Основні й резервні одноразові коди; тільки HMAC. |
| unit_installations | Активовані комп’ютери, token digest і останній зв’язок. |
| unit_metric_snapshots | Майбутні агреговані цифри. |
| admin_audit_log | Дії з сідами, кодами та інсталяціями. |

RLS увімкнено без прямого доступу для anon та authenticated. Таблиці
використовує лише Edge Function із service_role.

## Адмінські ендпоінти admin-api

Базова адреса:

~~~text
https://<project-ref>.supabase.co/functions/v1/admin-api
~~~

| Метод і шлях | Дія |
| --- | --- |
| POST /deployments | Приймає лише seed та issuePrimaryCode; повертає deploymentId, версію, digest і код. |
| PUT /deployments/:id/seed | Приймає новий seed та expectedVersion. |
| GET /deployments/:id/status | Повертає статус, версію, digest, коди та інсталяції. |
| POST /deployments/:id/status | Призупинити, відновити або архівувати. |
| POST /deployments/:id/activation-codes | Створити основний або резервний код. |
| POST /deployments/:id/activation-codes/:codeId/revoke | Відкликати код. |
| POST /deployments/:id/installations/:installationId/revoke | Відключити інсталяцію. |
| GET /deployments/:id/audit | Історія дій. |

Перший запит не містить окремих полів структури:

~~~json
{
  "seed": "SHU1.eyJmb3JtYXQiOiJzaGFibG9uaXphdG9yLXVuaXQtc2VlZCIsLi4ufQ",
  "issuePrimaryCode": true
}
~~~

Відповідь:

~~~json
{
  "deploymentId": "uuid",
  "seedVersion": 1,
  "seedDigest": "sha256-or-hmac",
  "issuedCode": {
    "id": "uuid",
    "kind": "primary",
    "label": "Основний код",
    "status": "pending",
    "codeHint": "F4Q7K",
    "plainCode": "UNIT-AAAAA-F4Q7K",
    "createdAt": "2026-09-24T12:00:00Z"
  }
}
~~~

## Клієнтські ендпоінти

| Метод і шлях | Дія |
| --- | --- |
| POST /client/activate | Перевіряє короткий код і повертає opaque seed, його версію та device token. |
| POST /client/heartbeat | Оновлює останній зв’язок і повідомляє про нову версію сіду. |
| GET /client/seed | Повертає актуальний opaque seed активній інсталяції. |
| POST /client/metrics | Приймає дозволені агреговані цифри. |

Для heartbeat, seed і metrics використовується заголовок
Authorization: Device <deviceToken>.

## Обов’язкові перевірки

- Edge Function не декодує сід у таблиці й не логує його вміст.
- Адмінські запити не приймають shortName, structure, unitType або інші окремі
  поля підрозділу.
- Digest сіду використовується для цілісності та ідемпотентності.
- Код генерує лише сервер і показує відкритим текстом один раз.
- Один код активує одну інсталяцію.
- Повтор із тим самим installationUid ідемпотентний, з іншим повертає 409.
- Зміна локального скелета створює новий сід і seedVersion.
- Клієнт застосовує новий сід тільки після перевірки формату та digest.
- Оновлення інсталятора й активаційний сід — незалежні механізми.

## Підключення

1. Застосувати SQL-міграцію.
2. Розгорнути Edge Function за цим контрактом.
3. Додати SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, ADMIN_API_KEY,
   ACTIVATION_PEPPER та DEVICE_TOKEN_PEPPER.
4. У адмінській редакції вказати URL функції.
5. Переконатися, що POST /deployments містить лише seed.
6. Активувати чистий клієнт і перевірити локально відновлений скелет.
