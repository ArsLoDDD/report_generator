# Архітектура Template Language v2

## Причина зміни

v1 поєднував англійські шляхи, скорочені глобальні назви й окремі правила для однієї та кількох осіб. Це створювало розбіжності між Довідником, валідатором і Rust-генератором. v2 має одну українську схему, нумерацію від 1 і однакові правила в усьому застосунку.

## Схема і реєстр

Єдине джерело правди — `src/shared/template-language/registry.v2.json`. Воно містить поля військовослужбовця, ролі й поля підписантів, поля документа, типи, приклади, доступність відмінків та модифікатори. TypeScript імпортує JSON для Довідника, конструктора і клієнтської перевірки. Rust вбудовує той самий JSON через `include_str!` для валідації та генерації. Окремих списків дозволених змінних немає.

Токен має вигляд `{{назва:модифікатор:модифікатор}}`. Військовослужбовець — `військовий_{номер}_{поле}`, підписант — `{роль}_{поле}`, дата — `дата_рапорту`. Для додаткового поля використовуються `військовий_{номер}_custom_{fieldKey}`, `автомобіль_{номер}_custom_{fieldKey}` і зв’язаний варіант `військовий_{номер}_автомобіль_{номер}_custom_{fieldKey}`. `fieldKey` незмінний; українська display name призначена лише для інтерфейсу.

Динамічні ролі підписантів визначаються за підтримуваним суфіксом поля та заповнюються тільки налаштуваннями. Ручні параметри не мають права перезаписувати підписанта або значення з БД. Для нових ручних параметрів рекомендовано префікс `параметр_`; довільні українські токени без префікса залишені для сумісності, крім очевидних помилок у стандартних назвах.

## Сумісність і міграція

Валідатор і генератор мають вузький адаптер читання для історичного синтаксису v1. Він розпізнає `soldier.{field}`, `soldiers[{zeroBasedIndex}].{field}`, `mainRank`, `mainName`, `mainPosition`, `mainSignature`, `commanderName` і `chiefName`, перетворює їх на поточні поля й бере участь у розрахунку вимог вибору. `mainSignature` повертає порожнє значення, як і стара реалізація. TypeScript і Rust використовують однаковий перелік aliases; end-to-end тести перевіряють, що старий DOCX проходить валідацію та генерується без незамінених токенів.

Цей адаптер не є другою публічною мовою: старі aliases не показуються у Конструкторі та не генеруються Аналізатором. Нові користувацькі шаблони створюються лише у v2. Невідомий англійський шлях не перетворюється на довільний ручний параметр, тому друкарські помилки у старому шаблоні залишаються явними помилками.

Схема БД має версію 5. Міграція створює `custom_field_template_aliases` і запам’ятовує попередні нормалізовані українські назви кожного кастомного поля. Alias переживає перейменування; після видалення поля лишається tombstone для зрозумілої помилки залежного шаблону. Збережена стать має пріоритет; за її відсутності допускається визначення за по батькові з явною помилкою, якщо визначення неможливе.

## Морфологія і розширення

Pipeline застосовує довільну кількість сумісних модифікаторів зліва направо. Реєстр контролює сумісність за типом. Звання мають контрольовані форми, посади — словник термінів та загальні правила. Нові ручні винятки додаються у морфологічний сервіс без зміни синтаксису шаблонів.

Текстові модифікатори: `великими`, `маленькими`, `з_великої`. Форматувальні модифікатори: `жирним`, `підкреслити`. Вони не змінюють значення, а передають форматування до DOCX.

Кастомне поле описується ключем, українською назвою, поясненням і початковим значенням. Початкове значення записується всім наявним військовослужбовцям і автоматично додається новим записам.

Опис кастомних змінних зберігається у `custom_variables.json` поруч із виконуваним файлом програми. Файл створюється під час першого додавання поля, а наступні поля додаються до нього без перезапису вже наявних описів. Під час запуску програма синхронізує цей файл із таблицями SQLite.

## Перевірка, генерація та цілісність DOCX

Перевірка шаблону й генерація використовують один Rust-парсер. Перед початком UI чекає завершення перевірки саме поточного шляху, показує всі помилки та блокує створення за невалідного шаблону або незаповнених обов’язкових параметрів. Кількість потрібних сутностей визначається найбільшим номером у токенах; порядок вибору є частиною контракту.

Генератор обробляє підтримувані Word stories, перевіряє баланс фігурних дужок і не дозволяє токену перетинати межу абзацу. Форматувальні модифікатори застосовуються лише до заміненого фрагмента і зливаються з наявним `w:rPr`. Після запису всі підтримувані XML-частини перевіряються повторно: невирішений токен або пошкоджений ZIP не публікується. DOCX з macro/ActiveX/OLE/embedded-вмістом відхиляється, а обмеження на кількість і розмір архівних записів захищають від непропорційного розпакування.

Результат спочатку записується в унікальний частковий файл, синхронізується й лише після перевірки публікується без перезапису наявного документа. Поруч створюється атомарний `*.docx.manifest.json` із версією формату, часом і версією застосунку, шляхом/назвою/hash шаблону, вибраними ID, параметрами та hash результату. Історія згенерованих рапортів читає цей manifest, а для старих документів без нього використовує сумісний fallback за файловими метаданими.

## Аналізатор готового рапорту

Аналізатор працює лише з DOCX і створює новий шаблон, не змінюючи джерело. Backend формує пропозиції з даних БД та налаштувань, рахує лише цілі збіги й призначає різним знайденим особам стабільні номери. Точний унікальний збіг має високу довіру й може бути вибраний автоматично; повтор, структурно визначена особа або наближений збіг підписанта має середню довіру та потребує підтвердження.

Ручна заміна приймає довільний текст, але значення, схоже на токен, обов’язково проходить парсер і registry. Попередній перегляд оновлюється із затримкою, будується поза видимим DOM і публікується лише для останньої ревізії. Перед створенням повторюється та сама трансформація як preflight. Fingerprint вихідного файла перевіряється під час аналізу, preview і створення; зміна DOCX у Word робить стан застарілим і вимагає повторного аналізу.

## Стратегія тестування

TypeScript-тести перевіряють реєстр, парсер, aliases v1, усі відмінки, стать, складні імена, регістр, вимоги вибору й захист від застарілих відповідей. Rust-тести перевіряють той самий реєстр, v1→v2 mapping, помилки, конфлікти, послідовний pipeline, морфологію, Word runs, межі абзаців, архівні обмеження й вихідний DOCX. Інтеграційні сценарії охоплюють створення/міграцію БД → перевірку контрольного DOCX → генерацію → повторну перевірку архіву та відсутності незамінених токенів, а також генерацію історичного v1-шаблону.
